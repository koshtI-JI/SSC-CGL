You are the lead full-stack engineer, architect, security engineer, data-integrity engineer, QA engineer and release engineer for this repair project.

Never report “fixed”, “secure”, “tested”, “deployed” or “working” merely because code was generated. Each claim must have an actual verification result.

## 0.4 No invented credentials or data

# 3. ACCOUNT IDENTITY — CRITICAL REPAIR

This is a high-priority data-integrity defect. Treat account identity and login username as separate concepts.

## 3.1 Canonical identities that must be preserved

| Person/account | Immutable application UID | Current login ID | Previous login ID |
|---|---|---|---|
| Damini | `damini_01` | `damini_888` | `damini_01` |
| Demo | `demo_123` | `demo@123` | — |

Rules:

- Damini's permanent application UID is `damini_01`.
- `damini_888` is the current mutable login ID, not a new student UID.
- The old username `damini_01` must not become a second Damini account.
- Demo's permanent application UID is `demo_123`.
- Demo's login ID is `demo@123`.
- Never derive an existing account's permanent identity from the current username.
- Never rewrite historical attempts, XP ledger entries, revisions or backups simply because a login ID changes.
- For new accounts, use a generated immutable application UID; do not use a mutable login name as the permanent ID.

## 3.2 Confirmed root cause: real accounts are filtered as dummy accounts

In the uploaded archive, `src/utils/sessionAndOverrides.ts` contains `BLOCKED_DUMMY_UIDS` with all of these values:

- `admin_preview`
- `damini_01`
- `damini_888`
- `demo_123`
- `dummy_student`
- `test_dummy`

`isRealCohortStudentUid()` rejects every value in that set. This is incompatible with the real Damini and Demo accounts.

The separate `SYSTEM_PLACEHOLDER_UIDS` set contains the intended placeholder IDs (`admin_preview`, `dummy_student`, `test_dummy`). The source comments say legitimate invited accounts should remain eligible, but the admin-specific function has an additional incorrect deny list.

This filter is used in the admin cohort/analytics/proctoring and roster flows. `buildAdminUserManagementRows()` in `src/utils/adminCommandCenter.ts` calls it for invite, student, presence and leaderboard records. Consequently, Damini and Demo can be eligible for their own dashboards and still disappear from Admin User Management and admin cohort views.

The current tests in `src/utils/sessionAndOverrides.test.ts` explicitly expect `damini_01`, `damini_888` and `demo_123` to be false. Update these tests to reflect the correct business rule. Do not leave a regression test that reintroduces the defect.

### Required fix

- Define one clear policy: exclude only actual internal/system placeholders from student cohort views.
- Do not hard-code real student UIDs or mutable login IDs in a “dummy” deny list.
- Make eligibility depend on authoritative active cohort membership/invite identity and explicit system placeholders.
- Ensure `allowedCohortUids` semantics do not accidentally allow all entries when an empty set is supplied unless that is an intentional, tested contract. Document that behavior.
- Update all callers consistently: admin user roster, cohort progress, leaderboard, presence, live proctor and analytics.
- Add tests for both real accounts and each actual placeholder.

Acceptance tests:

1. Damini `damini_01` appears once in Admin User Management.
2. Her displayed login is `damini_888` when the latest authoritative account record says so.
3. Her stable UID stays `damini_01` after a login rename.
4. Demo `demo_123` appears once, with login `demo@123`.
5. `admin_preview`, `dummy_student` and `test_dummy` do not appear as real students.
6. A login rename does not create a second roster row or split attempts/XP.

## 3.3 Confirmed root cause: stale profile can override newer invite identity

In `buildAdminUserManagementRows()` the inspected code uses:

- `loginId: stu?.loginId || inv.loginId`
- `displayName: stu?.displayName || inv.displayName`
- `targetPost: stu?.targetPost || inv.targetPost ...`

This always prefers a student profile when it exists, even when the VIP invite was edited more recently. Admin can therefore see a stale username/name/target post.

### Required fix

- Establish which document is authoritative for login and account status. In the current architecture, the VIP invite is the login/credential/account-control record; the student profile is the educational profile and historical progress record.
- For overlapping profile fields, use an explicit merge policy with timestamps and field ownership. Do not blindly choose “latest entire object” if it can overwrite student-only fields.
- The login ID, active state and credential metadata must come from the authoritative account record.
- Display name/target post edits must update invite and student profile consistently, but failures must be surfaced and queued (see Section 7).
- Use `createdAt` and `updatedAt` consistently, normalizing Firestore Timestamps and numeric local timestamps without comparing incompatible representations naively.
- Add an account row field for account creation time so Admin can display it.

Acceptance: edit profile/admin fields, refresh, log out/in, and confirm the same current values appear in the student profile, admin roster and leaderboard without losing student-specific fields.

## 3.4 Confirmed password exposure in Admin UI and data model

In the uploaded source:

- `AdminUserManagementRow` has a `password` field.
- `buildAdminUserManagementRows()` assigns `password: inv.currentPassword ?? null`.
- `AdminUserManagementTab.tsx` includes password reveal/copy functionality and password inputs using text rendering in parts of the form.
- `VipInvite` type includes optional `currentPassword`.
- `firestore.rules` explicitly permits the optional `currentPassword` field in a VIP invite document.
- Create/update VIP account functions write plaintext `currentPassword` alongside a hash.
- Local fallback and snapshot export paths also copy this field.

This is a confirmed security defect, not just a UI issue.

### Required fix

- Remove password values from roster row types, list queries, view models, analytics, debug output and UI.
- Never display or copy an existing password in the Admin Panel.
- All password/new-password inputs must use `type="password"`, with optional show/hide only for the newly typed value and never for an existing stored value.
- Remove plaintext password writes from new account creation and account edits.
- Stop accepting the `currentPassword` property in new data validation and new persistence paths.
- Add a migration plan to remove legacy plaintext values from Firestore, LocalStorage, IndexedDB and report/snapshot files after backup and approval.
- Do not delete live legacy fields before a verified backup and approved staging migration.
- Do not print old values in migration logs.
- Sanitize `exportLocalCohortSnapshot()` and all backup/export paths so credentials and authentication metadata are excluded.

Do not confuse “remove plaintext from the UI” with “secure authentication”. The current authentication architecture itself must be addressed in Section 5.

## 3.5 Account lifecycle and duplicate protection

Implement a safe account lifecycle:

- Create: generated immutable UID; normalized, unique login ID; duplicate/collision checks; account creation timestamp.
- Rename login: update login ID only; keep UID and history unchanged.
- Edit profile: update owned fields consistently.
- Activate/deactivate: preserve all records; prevent a deactivated user from starting new sessions/tests; do not delete progress.
- Password recovery: only through an authentication mechanism that can securely prove or reset identity.
- Archive/revoke: soft-state transition; retain tests, responses, XP and reports.
- Delete: do not expose destructive hard delete for a student account without a separate, explicit retention/export policy and owner approval.

Check login-ID normalization collisions. `loginIdToKey()` in `src/utils/examEngine.ts` lowercases/trims and replaces non-alphanumeric characters with underscores. Therefore `demo@123` maps to `demo_123`. Test collisions such as different punctuation producing the same normalized key before creating/updating an account.

The account creation code currently stores invites by normalized login key. Existing account documents must retain their current document IDs during a rename. Do not “fix” Damini by moving her account document from `damini_01` to `damini_888`.

The inspected code enforces a maximum of five in account creation, but does not clearly enforce unique slot numbers. Report the current slot-number anomalies and determine the intended slot policy. Do not silently reassign any live slot.

## 3.6 Password reset limitation

The current project has no Firebase Authentication SDK integration and no secure browser-only way to reset another user's Firebase Authentication password. Do not fake a reset button that only changes local state or updates an insecure hash.

A static frontend can:

- Let a signed-in user change their own password through Firebase Authentication with recent reauthentication.
- Send a reset email to a real, verified/reachable email address using Firebase Authentication, if the account has one.
- Offer a manual owner-operated reset through Firebase Console when the account uses a username without a reachable email, if that is the chosen no-backend process.

A frontend client must not be able to set arbitrary passwords for other accounts using privileged credentials. If programmatic admin-set password is required, it needs a trusted administrative capability (for example a managed server-side function) which conflicts with the strict “no custom backend” constraint. Do not add one without explicit approval.

Before implementation, present the practical options and limitations for `damini_888` and `demo@123`; do not invent email addresses. Keep the existing application usable until a safe migration is approved and tested in staging.

# 5. AUTHENTICATION AND FIRESTORE SECURITY — P0 BLOCKER

This section is a hard safety gate.

## 5.1 Confirmed current architecture

The uploaded source:

- Imports Firebase App and Firestore, but no `firebase/auth` SDK module was found under `src/`.
- Performs admin/student password checks in browser code inside `src/lib/firestoreService.ts`.
- Uses deterministic SHA-256 hashes with fixed prefixes: `sankalp_vip_v1:` for student passwords and `sankalp_admin_v1:` for admin passwords.
- Stores/fetches hashes from Firestore/client-visible records and LocalStorage fallback.
- Uses browser `sessionStorage` key `getcgl_session_v1` for role/UID session data.
- Restores admin session by checking app-level admin ID/credentials, not by validating a Firebase Authentication signed-in principal.

A deterministic SHA-256 hash with a fixed prefix is not a password-hashing scheme designed to resist offline guessing. The browser verifies the hash, so the current app-level username/password gate is not a secure identity boundary.

## 5.2 Confirmed Firestore rules problem

In the uploaded `firestore.rules`:

- A global catch-all rule says `allow read, write: if false`.
- Collection-specific matches then add their own `allow get`, `allow list`, `allow create`, `allow update` or `allow delete` conditions.
- Firestore authorization combines matching allow rules permissively (a matching allow can grant access); the global deny does not cancel a more specific allow.
- The inspected entire rules file contains no `request.auth`, `request.auth.uid`, auth claims, admin lookup or signed-in-user check.
- Some collection rules permit reads using only document ID or data-shape constraints.
- VIP invite validation allows `currentPassword`.

The result is that schema validation is being used where identity/ownership authorization is required. A person who can access the Firebase project through the web client may be able to read/write data allowed by a schema rule without proving the intended user/admin identity. This is a P0 security issue.

Examples visible in the current rules include:

- Settings `get` for IDs including `adminCredentials`.
- VIP invite `get` based on a valid document ID and `list` based on slot range.
- Student `get` based on a valid student UID.
- Several other collections with schema/data predicates but no authenticated-owner/admin check.

Do not claim the global deny makes these collections safe.

## 5.3 Required target design without a custom server

The owner does not want a custom backend. Respect that constraint.

A safe direction to evaluate is Firebase Authentication (managed service) plus strict Firestore Security Rules:

- Use Firebase Authentication to establish `request.auth`.
- Keep the application's canonical student UID independent of a mutable login ID and independent of Firebase Auth UID.
- Add an explicit mapping between Firebase Auth UID and the existing stable application UID. For example, an owner-created account-link document can map `request.auth.uid` to `canonicalStudentUid`; never allow a student to create or edit their own privileged mapping.
- Provision admin authorization through a trusted owner-controlled process (manual Firebase Console setup or a correctly secured managed claim process). Never let a client create its own admin marker.
- Rules must verify that the authenticated Firebase user is the mapped owner for student profile, attempts, drafts, responses, revision vault, progress and other private student records.
- Admin-only collections and writes must require an actual admin authorization condition.
- Publicly readable question/test content may remain readable only where intended; writes must be admin-only.
- Do not store admin password hashes in a publicly readable `settings` document.
- Do not expose `vipInvites` credential data to all signed-in students.
- Define least-privilege access for every collection and subcollection.
- Keep progress/attempt deletion prohibited where the existing product policy requires immutable history.

Important identity detail: Firebase Auth UIDs generated by the client may not match the existing application UIDs `damini_01` and `demo_123`. Do not change the application UID just to match Firebase Auth. Preserve the app UID and add a secure mapping, with staging tests for all queries and writes.

## 5.4 Username login and reset constraints

Current IDs include `damini_888` and `demo@123`; neither is necessarily a reachable email address. Firebase Authentication email/password login and reset-email workflows require an email-style identifier, and a client-only admin cannot securely set another user's password.

Before code changes, present a migration design that answers:

1. How will a username map to the Firebase Auth account?
2. Does each student have a genuine email address, or will the owner choose an internal synthetic login alias?
3. What happens when the user forgets a password and has no reachable email?
4. How will the owner reset access without a custom backend?
5. How will existing password hashes and plaintext values be retired safely?
6. How will existing sessions be invalidated and reissued?
7. How will offline access work after the cloud authentication model changes?
8. How will existing UIDs and history stay stable?

Do not invent email addresses or silently choose a synthetic-email scheme. If synthetic addresses are considered, explicitly explain that an email reset message cannot reach the user and owner-operated recovery will be needed.

## 5.5 Security migration approval gate — do not cross automatically

Before changing production rules or migrating real accounts:

- Build a separate Firebase staging project (or use a separate named Firestore database only if security and configuration isolation are proven).
- Add Firebase Auth only in a development branch.
- Create staging user accounts and explicit UID-to-app-UID mappings.
- Write least-privilege Firestore rules.
- Add automated Rules Unit Testing (Firebase Emulator Suite if available) using `security_spec.md` as an initial adversarial test list.
- Verify all currently expected workflows under the new rules.
- Back up production records without exporting passwords or secrets.
- Produce an explicit field-by-field migration plan and rollback plan.
- Ask the owner for approval before any production user/rule/data change.

Never deploy new rules to production before tests prove that:
- anonymous reads/writes are denied for private data;
- a student cannot read another student's data;
- a student cannot modify another student's progress;
- a student cannot read credentials or admin settings;
- a student cannot create or elevate an admin account;
- a student cannot publish/edit tests or questions;
- an admin can perform intended cohort management;
- public question/test reads (if required) remain functional;
- immutable attempts/progress cannot be deleted.

If this security model cannot be made safe under the no-custom-backend constraint, explain the limitation and stop. Do not ship insecure rules to preserve a superficial login experience.

## 6.6 Sync defects to repair

### A. Partial update errors are silently ignored

In `updateVipUser()` the invite document is updated, then profile and leaderboard records are updated separately. The inspected code catches and ignores some profile/leaderboard update failures (`.catch(() => {})`) and then applies local state. The offline queue operation is for the VIP invite, not necessarily for every dependent record.

This can leave Firestore invite, student profile and leaderboard inconsistent while the UI appears successful.

Required repair:

- Do not swallow errors.
- Use an appropriate Firestore batch/transaction when all writes are atomic and size/semantics permit.
- If operations cannot be atomic, implement an explicit durable outbox with a separate operation for each dependent document.
- Mark each operation pending/synced/failed with retry count and last error (without sensitive content).
- Make retries idempotent.
- Show a clear sync status to Admin.
- Do not display success until the intended write is either committed remotely or clearly marked as locally queued.
- Add tests for partial failure at each write step.

### B. Pending sync queue cap

The inspected LocalStorage code truncates `pendingSyncOps` to the latest 500 entries (`slice(-500)`). Tombstone collections are also capped. Silently dropping the oldest unsynced operation/tombstone can lose a user change or allow a deleted stale record to reappear.

Required repair:

- Never silently discard an unacknowledged data operation.
- If storage is near capacity, surface a durable sync warning and preserve the outbox.
- Use compaction only when operations are provably superseded by a later acknowledged operation for the same entity/document.
- Keep tombstones until the corresponding remote delete/archive is confirmed and reconciliation proves stale data cannot resurrect.
- Define queue schema versioning and migration tests.

### C. Account deletion is inconsistent and destructive

The inspected `deleteVipInvite()` removes the invite, leaderboard, presence and proctor records (some best-effort) and deletes local student/leaderboard/revision data, but the student parent document is configured as non-deletable by Firestore rules. Historical attempts and XP are retained. This can create a ghost profile remotely and destroy local history.

Required repair:

- Replace normal “delete student” UI with deactivate/archive/revoke access.
- Keep student profile, attempts, responses, XP ledger and revision history.
- Only remove ephemeral presence/proctor state where appropriate.
- Make account reactivation possible without creating a second identity.
- Any genuine data-erasure flow needs a separately approved policy and a full export/backup first.

### D. Snapshot import needs dry-run/conflict handling

Inspect `importLocalCohortSnapshot()` and related export/import code. The archive includes whole-database snapshot logic. It must never import password hashes/plaintext credentials or blindly overwrite canonical data.

Required repair:

- Add import preview/dry-run.
- Validate schema/version and record counts.
- Strip all authentication secrets and credential metadata from exported/imported cohort snapshots.
- Identify entity conflicts by stable ID and timestamp/explicit ownership.
- Deduplicate attempts and XP by immutable entry/document IDs.
- Reject malformed or unknown data instead of silently normalizing away important values.
- Show exact create/update/skip/conflict counts before commit.
- Require explicit confirmation before applying imports.
- Retain the previous state for rollback.

### E. Cloud-first / offline behaviour

Keep the existing cloud-first approach when online and LocalStorage/IndexedDB fallback when offline. Test offline bootstrapping, going online, queue replay, duplicate writes, local tombstones and quota failure.

Never assume “online” means a Firestore write succeeded. Distinguish:

- local-only;
- pending upload;
- server confirmed;
- failed/retryable;
- permanently rejected (e.g. permission denied/schema error).

Do not endlessly retry permanent authorization failures.

### F. Data migration versioning

Add a versioned schema/migration path for LocalStorage/IndexedDB changes. Never change an existing stored field shape without a migration test and old-data fixture. Preserve exam drafts across app upgrades wherever possible.
